# The diagnostic catalog

Every diagnosis x12-doctor can make. Each one states what it checks, why real
integrations produce it, and what to change — because a code and a line number
is not an answer to "why did my order not arrive".

Eighteen of these mirror a fault in
[`@adeloi/edi-fixtures`](https://github.com/Adeloi-Official/edi-fixtures) one
for one. That library generates the broken document; this one diagnoses it. The
correspondence is asserted by the test suite in both directions, so a fault
added there without a diagnosis here fails the build.

`x12doctor codes` prints this catalog in the terminal, and `x12doctor codes A02`
explains a single entry.

## Severity

| Severity | Meaning |
|---|---|
| `error` | The document is wrong. A partner will reject it, or has. |
| `warning` | Legal, but a common cause of rejection or silent misreading. |
| `info` | Worth knowing. Normal in some workflows. |

`--fail-on` decides which of these makes the command exit non-zero. It defaults
to `error`.

## A — Structure & envelope

### `A00` — Not an X12 interchange

**Severity:** `error` · **Applies to:** any

**What it checks:** The file contains no ISA segment, or no readable segments at all.

**Why it happens in production:** Usually the wrong file was picked up: an EDIFACT message, a CSV export, an
HTML error page saved by a failed download, or a zero-byte file left
behind by an interrupted transfer.

**How to fix it:** Confirm the file is the X12 payload itself and not an envelope, archive or
transport artefact wrapping it.

### `A01` — ISA is not 106 characters

**Severity:** `error` · **Applies to:** any

**What it checks:** The ISA segment must be exactly 106 characters including its terminator,
with every element padded to a fixed width.

**Why it happens in production:** The ISA is the only fixed-width segment in X12, so code that builds it by
joining trimmed strings produces a short ISA that looks fine to the eye.
Receivers read ISA16 and the terminator by byte offset, so a single
missing space shifts everything.

**How to fix it:** Pad each ISA element to its defined width with spaces — notably ISA02 and
ISA04 to 10, ISA06 and ISA08 to 15, ISA13 to 9 digits. Never trim the ISA.

**Matching fixture:** `faults.isaTruncated()` in `@adeloi/edi-fixtures` produces a document that triggers this.

### `A02` — SE segment count is wrong

**Severity:** `error` · **Applies to:** any

**What it checks:** SE01 must equal the number of segments from ST through SE inclusive.

**Why it happens in production:** The count is written when the transaction set is assembled, then a segment
is added or removed afterwards — a conditional REF, an extra line item, a
stripped-out empty segment — and the count is never recalculated.

**How to fix it:** Count ST through SE inclusive and write that number into SE01. Compute it
after the transaction set is complete, never before.

**Matching fixture:** `faults.seCountWrong()` in `@adeloi/edi-fixtures` produces a document that triggers this.

### `A03` — Control numbers do not match

**Severity:** `error` · **Applies to:** any

**What it checks:** ISA13 must equal IEA02, GS06 must equal GE02, and ST02 must equal SE02.

**Why it happens in production:** The trailer is generated separately from the header, often from a
different counter or a re-read of a sequence table. Any retry or restart
between the two writes leaves the pair out of step.

**How to fix it:** Carry the control number through in one variable and write the trailer
from that same value rather than fetching it twice.

**Matching fixture:** `faults.controlNumberMismatch()` in `@adeloi/edi-fixtures` produces a document that triggers this.

### `A04` — Duplicate interchange control number

**Severity:** `error` · **Applies to:** any

**What it checks:** The same ISA13 appears on more than one interchange from the same sender
within the scanned set.

**Why it happens in production:** A counter reset after a redeploy, a database restore, or a re-send that
reused the original number. Most receivers reject duplicates outright as
replay protection, so the second document silently never arrives.

**How to fix it:** Store the interchange counter where it survives restarts and never reuse a
number, not even for a corrected resend.

**Matching fixture:** `faults.duplicateIsaControl()` in `@adeloi/edi-fixtures` produces a document that triggers this.

### `A05` — Nonstandard or inconsistent separators

**Severity:** `warning` · **Applies to:** any

**What it checks:** The element, segment or component separator is unusual, or it differs from
what the ISA declares.

**Why it happens in production:** Separators are declared per interchange, so anything is legal in principle
— but a hand-edited file, a spreadsheet round trip, or a concatenation of
documents written by two different systems leaves the declaration and the
body disagreeing.

**How to fix it:** Make the writer take its separators from one place and check them against
ISA16 and the ISA terminator before sending.

**Matching fixture:** `faults.nonstandardSeparators()` in `@adeloi/edi-fixtures` produces a document that triggers this.

### `A06` — GE transaction set count is wrong

**Severity:** `error` · **Applies to:** any

**What it checks:** GE01 must equal the number of ST segments in the functional group.

**Why it happens in production:** Transaction sets are appended to a group in a loop while GE01 is written
from a count captured before the loop, or from a filtered list that
dropped an empty document.

**How to fix it:** Write GE01 from the length of the list you actually serialised.

### `A07` — IEA functional group count is wrong

**Severity:** `error` · **Applies to:** any

**What it checks:** IEA01 must equal the number of GS segments in the interchange.

**Why it happens in production:** Same cause as a wrong GE01, one level up: groups are added or merged after
the trailer count was decided.

**How to fix it:** Write IEA01 from the number of groups actually written.

### `A08` — Unexpected version identifier

**Severity:** `warning` · **Applies to:** any

**What it checks:** ISA12 and GS08 must carry a recognised X12 version, and the two must
describe the same release.

**Why it happens in production:** Version strings get hard-coded once and then survive an upgrade. An ISA
claiming 00401 under a GS claiming 005010 typically means the envelope
writer and the document writer were upgraded at different times.

**How to fix it:** Set ISA12 and GS08 from the same configured version. For 4010 these are
00401 and 004010 respectively.

### `A09` — Content outside the interchange

**Severity:** `warning` · **Applies to:** any

**What it checks:** Characters appear before the ISA or after the IEA that are not part of any
segment.

**Why it happens in production:** A transport header, a shell banner, or a log line got prepended when the
file was written or copied. Strict receivers refuse the whole interchange
on the first unexpected byte.

**How to fix it:** Write the payload with no wrapper. If a transport adds framing, strip it
before the file reaches the translator.

### `A10` — Envelope is not closed

**Severity:** `error` · **Applies to:** any

**What it checks:** Every ISA needs an IEA, every GS a GE, and every ST an SE.

**Why it happens in production:** The file was truncated in transit, the writer crashed mid-stream, or an
exception skipped the code that emits the trailer. A truncated file often
still parses far enough to look plausible.

**How to fix it:** Compare the byte count against what the sender recorded and request a
resend. Emit trailers from a finally block so a partial document is never
written.

### `A11` — Envelope segments out of order

**Severity:** `error` · **Applies to:** any

**What it checks:** Envelope segments must nest strictly: ISA, GS, ST, business segments, SE,
GE, IEA.

**Why it happens in production:** Two interchanges were concatenated without their trailers, or a batch
writer interleaved documents. It also happens when files are merged by a
shell script that assumes one document per file.

**How to fix it:** Split the file back into one interchange per ISA/IEA pair and check
whether the merge step is supposed to exist at all.

## B — Semantics & content

### `B01` — Nonstandard unit of measure

**Severity:** `warning` · **Applies to:** any

**What it checks:** Unit of measure elements must carry a two-character X12 code, not a
spelled-out word.

**Why it happens in production:** The value came straight from an ERP field that stores display text, so a
spelled-out unit passes internal validation — internally it was never a
code at all.

**How to fix it:** Map the internal unit to its X12 code at the boundary and reject unmapped
values instead of passing them through.

**Matching fixture:** `faults.uomNonstandard()` in `@adeloi/edi-fixtures` produces a document that triggers this.

### `B02` — Suspected implied decimal error

**Severity:** `warning` · **Applies to:** any

**What it checks:** A monetary or quantity value looks scaled by a factor of 100 or 1000
relative to its neighbours.

**Why it happens in production:** Some partners expect implied decimals, where 1000 means 10.00. Mixing a
system that applies the convention with one that does not multiplies or
divides every amount on the document.

**How to fix it:** Confirm the partner's decimal convention, then apply it in one place.
Cross-check the line extended price against quantity times unit price.

**Matching fixture:** `faults.impliedDecimals()` in `@adeloi/edi-fixtures` produces a document that triggers this.

### `B03` — Wrong date format

**Severity:** `error` · **Applies to:** any

**What it checks:** Date elements must match the length their version defines: six digits
(YYMMDD) or eight (CCYYMMDD), depending on the element.

**Why it happens in production:** The 4010 release mixes both widths across segments — ISA09 is six digits
while DTM02 is eight — so a single shared date formatter emits the wrong
width somewhere. Y2K-era code that was never revisited produces the same
result.

**How to fix it:** Format each date from its element definition rather than from one global
pattern. Do not zero-pad a short year into a long one.

**Matching fixture:** `faults.dateFormatShort()` in `@adeloi/edi-fixtures` produces a document that triggers this.

### `B04` — CTT totals do not match

**Severity:** `error` · **Applies to:** any

**What it checks:** CTT01 must equal the number of line items, and CTT02 when present must
equal the sum of the quantities.

**Why it happens in production:** Line items are filtered after the totals are computed — cancelled lines
removed, zero-quantity lines dropped — and CTT is not recomputed. It is
the check most translators run first.

**How to fix it:** Compute CTT from the serialised line items as the last step before writing
the trailer.

**Matching fixture:** `faults.cttMismatch()` in `@adeloi/edi-fixtures` produces a document that triggers this.

### `B05` — Required partner reference is missing

**Severity:** `error` · **Applies to:** any

**What it checks:** A REF qualifier the partner profile marks as required does not appear in
the document.

**Why it happens in production:** The reference is optional in the X12 standard but mandatory in the
partner's implementation guide, so nothing but the partner's own validator
catches it. Often the source field is simply empty for a subset of orders.

**How to fix it:** Add the qualifier to the document and make the missing source value a hard
failure upstream rather than an omitted segment.

**Matching fixture:** `faults.missingRef()` in `@adeloi/edi-fixtures` produces a document that triggers this.

### `B06` — Required segment is missing

**Severity:** `error` · **Applies to:** any

**What it checks:** A segment mandatory for this transaction set is absent — BEG in an 850,
BIG in an 810, BSN in an 856, BAK in an 855.

**Why it happens in production:** A conditional branch in the writer skipped it, or the document was
assembled from a template that predates the segment being required.

**How to fix it:** Add the segment. Validate the required set before serialising so the
document is never produced without it.

## C — Acknowledgments (997)

### `C01` — 997 reports errors

**Severity:** `info` · **Applies to:** 997

**What it checks:** The functional acknowledgment carries AK3, AK4, AK5 or AK9 codes
describing what the receiver objected to.

**Why it happens in production:** This is the receiver telling you why your document did not make it
through. The codes are numeric and undocumented in the file itself, which
is why a 997 is usually forwarded to a human unread.

**How to fix it:** Read the decoded reason below, fix the named segment or element in the
original document, and resend under a new control number.

### `C02` — 997 references an unknown group

**Severity:** `error` · **Applies to:** 997

**What it checks:** AK102 does not correspond to any functional group control number that was
sent.

**Why it happens in production:** The acknowledgment belongs to a different sender, the group counter was
reset so the number is ambiguous, or the 997 was generated against a
document that never left the outbox.

**How to fix it:** Match AK101/AK102 against your sent-group log. If nothing matches, the
acknowledgment was misrouted — check the ISA sender and receiver IDs on
both documents.

**Matching fixture:** `faults.fa997UnknownGroup()` in `@adeloi/edi-fixtures` produces a document that triggers this.

### `C03` — 997 rejected the document

**Severity:** `error` · **Applies to:** 997

**What it checks:** AK501 or AK901 reports status R (rejected) or E (accepted with errors), so
the document was not processed as sent.

**Why it happens in production:** The receiver's translator found a structural or syntactic problem it would
not accept. Nothing downstream of it ever saw the document, which is why
the order appears to have vanished.

**How to fix it:** Fix the segments named in the AK3/AK4 detail, then resend with a new ST02
and GS06. Do not resend the identical control numbers.

**Matching fixture:** `faults.fa997Rejected()` in `@adeloi/edi-fixtures` produces a document that triggers this.

### `C04` — Rejection located in the original document

**Severity:** `error` · **Applies to:** 997

**What it checks:** An AK3/AK4 position was resolved against the original document, naming the
exact segment and element the receiver objected to.

**Why it happens in production:** The 997 reports positions, not content, so on its own it says 'segment 14,
element 3' and nothing more. Pairing it with the original turns that into
the actual value that was rejected.

**How to fix it:** Correct the value shown here in the source system, not just in the
outbound file, or the next document will repeat it.

### `C05` — No acknowledgment received

**Severity:** `warning` · **Applies to:** any

**What it checks:** An interchange requested an acknowledgment (ISA14 = 1) but no 997 in the
scanned set references its group.

**Why it happens in production:** The document never reached the partner, or their acknowledgment never
reached you. Both look identical from your side, and both are usually
noticed only when someone asks about a missing order.

**How to fix it:** Check the transport logs for the interchange, then ask the partner whether
they received the group. Alert on unacknowledged interchanges rather than
waiting for the phone call.

**Matching fixture:** `faults.fa997Missing()` in `@adeloi/edi-fixtures` produces a document that triggers this.

### `C06` — Interchanges out of chronological order

**Severity:** `warning` · **Applies to:** any

**What it checks:** Documents in one business flow carry envelope timestamps that contradict
the order the flow must happen in — an ASN stamped before the
acknowledgment of the order it ships.

**Why it happens in production:** Documents are generated in a batch that stamps them all at run time rather
than at the moment of the business event, or two systems in the flow
disagree about the time zone. Receivers that process by envelope timestamp
then apply them in the wrong order.

**How to fix it:** Stamp ISA09/ISA10 and GS04/GS05 at the moment the document is produced, in
UTC, and never backdate a resend.

**Matching fixture:** `faults.outOfOrderInterchange()` in `@adeloi/edi-fixtures` produces a document that triggers this.

## D — Advance ship notices (856)

### `D01` — Broken HL hierarchy

**Severity:** `error` · **Applies to:** 856

**What it checks:** Every HL02 parent reference must point at an HL01 that appears earlier in
the document, and HL numbering must be sequential.

**Why it happens in production:** The shipment tree is built recursively and a level is emitted before its
parent, or a pack level is dropped for single-item shipments while its
children keep pointing at it. The item then belongs to nothing.

**How to fix it:** Number HL01 sequentially from 1 in document order and set HL02 from the
parent's already-assigned number.

**Matching fixture:** `faults.hlOrphan()` in `@adeloi/edi-fixtures` produces a document that triggers this.

### `D02` — Invalid SSCC-18 check digit

**Severity:** `error` · **Applies to:** 856

**What it checks:** An SSCC-18 in a MAN segment fails its GS1 mod-10 check digit, or is not 18
digits long.

**Why it happens in production:** The check digit was computed with the wrong weighting, or the label number
was truncated or zero-padded on the way into the document. Receiving docks
scan the physical label, so a mismatch stops the pallet at the door.

**How to fix it:** Recompute the check digit over the first 17 digits with weights 3 and 1
from the right, and verify the value matches the printed label.

**Matching fixture:** `faults.ssccInvalid()` in `@adeloi/edi-fixtures` produces a document that triggers this.

### `D03` — Shipped quantity does not match the order

**Severity:** `error` · **Applies to:** 856

**What it checks:** A quantity in the 856 differs from the quantity ordered for the same line
in the referenced 850.

**Why it happens in production:** A partial shipment was sent without splitting the line, units and cases
were mixed up, or the ASN was built from the pick list while the order was
later amended.

**How to fix it:** Reconcile against the purchase order before sending. For genuine partial
shipments, ship the correct quantity and let the balance follow on its own
ASN.

**Matching fixture:** `faults.asnQtyMismatch()` in `@adeloi/edi-fixtures` produces a document that triggers this.

### `D04` — Implausible shipment dates

**Severity:** `warning` · **Applies to:** 856

**What it checks:** The ASN's dates are not in a possible order — shipped after delivered, or
an ASN issued after the goods arrived.

**Why it happens in production:** The ASN is generated in a nightly batch rather than at dispatch, so it is
stamped later than the delivery it announces. Time zones applied to only
one of the two dates do the same thing.

**How to fix it:** Send the ASN at dispatch, and stamp every DTM from the same clock and time
zone.

**Matching fixture:** `faults.asnAfterDelivery()` in `@adeloi/edi-fixtures` produces a document that triggers this.

## Adding a diagnosis

Add an entry to `CATALOG` in `src/x12doctor/catalog.py`, raise it from a check
with `catalog.make_finding()`, then regenerate this file:

```sh
python tools/gen-docs.py
```

The test suite asserts that every catalog entry is raised somewhere, that every
raised code is in the catalog, and that this file is not stale.
